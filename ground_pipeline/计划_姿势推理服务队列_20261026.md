## 1. 背景与现状

姿势推理（`/v1|v2/pose/single`）与地面推理（`/v1/ground`）共用同一个进程、同一张 GPU、同一个 SAM3D 实例。当前并发处理方式是「快速失败」：

- 姿势接口用非阻塞 `pose_lock`，抢不到锁立即返回 `503 GPU 忙，请稍后重试`（[ground_service.py#L2103-L2105](file:///g:/UGit/Phy-SIC/ground_pipeline/ground_service.py#L2103-L2105)）。
- 任务登记表 `state["pose_tasks"]` 在**拿到锁之后**才写入（[ground_service.py#L2107-L2109](file:///g:/UGit/Phy-SIC/ground_pipeline/ground_service.py#L2107-L2109)），排队中的请求无法取消。
- `GroundPoseEstimator.infer` 内部另有一把**阻塞**的 `self._lock`（[ground_pose.py#L232](file:///g:/UGit/Phy-SIC/ground_pipeline/ground_pose.py#L232)、[ground_pose.py#L271](file:///g:/UGit/Phy-SIC/ground_pipeline/ground_pose.py#L271)），`/v1/ground` 的 `pose_inference` 分支直接调用它（[ground_service.py#L2478-L2504](file:///g:/UGit/Phy-SIC/ground_pipeline/ground_service.py#L2478-L2504)），既绕过 `pose_lock` 也没有超时与公平性。
- 多人（多个 Max 客户端 / 多个脚本）同时提交时，除第一个外的请求全部立刻失败；客户端只能自行重试，重试风暴又会放大失败率。

结论：GPU 本来就必须串行，真正缺的是**一个统一、有界、可观测、可取消的等待队列**，而不是更多的锁。

## 3. 目标与非目标

### 3.1 目标

1. **串行但有队列**：GPU 仍然单任务串行，第二个及之后的请求进入有界 FIFO 队列等待，正常容量内不再出现 `GPU 忙`。
2. **可取消**：排队中与执行中的任务都能按 `request_id` 取消；排队中取消立即释放等待位并让等待中的 HTTP 请求尽快返回。
3. **公平**：同一客户端最多占用 `N` 个等待位；支持整数优先级（交互任务优先于批量任务），并有基础防饿死。
4. **可观测**：`GET /v1/pose/queue`、`/v1/pose/health` 与 `GET /metrics` 暴露容量、排队数、当前任务、等待/执行耗时统计；日志按任务记录入队、开始、结束。
5. **统一入口**：`/v1/ground` 的 `pose_inference` 也走同一队列（低优先级），消除双锁竞争。
6. **不破坏现有协议**：成功响应只新增 `queue` 字段；`v2` XML 结构、字段、错误语义不变；队列满/超时仍用 503，旧客户端无需改代码。

### 3.2 非目标

- 不做多 GPU / 多进程 worker；GPU 串行是硬件约束，本计划只解决等待与调度。
- 不做异步任务接口（提交返回 `job_id` + 轮询）；保持现有「一个 HTTP 请求等到结果」的同步语义。
- 不做多人实例分离、批量多人推理（仍为单人单次）。
- 不改鉴权、计费、模型精度与推理耗时。

## 4. 方案总览

```
POST /v1|v2/pose/single
        │
        ▼
 解析 / 校验 / 读图 / 目标 profile 解析（请求线程，CPU）
        │  失败 → 400/413/503（不入队）
        ▼
 PoseQueue.submit(request_id, client_key, priority)
        │  满载 / 超配额 → 503 queue_full / client_quota（不入队）
        ▼
 等待（HTTP 线程阻塞，最长 wait_timeout）
        │  超时 → 503 queue_timeout，撤销排队
        │  取消 → 200 status=cancelled
        ▼
 ┌───────────────────── 单个 worker 线程（GPU 串行）─────────────────────┐
 │ 出队（优先级 + 等价 FIFO + aging）                                    │
 │ 人物分割 →（可选）地面推理 → SAM3D → 落地/重定向 → overlay → 响应 body │
 └──────────────────────────────────────────────────────────────────────┘
        │
        ▼
 写回 job.result → 唤醒等待线程 → 按 v1 JSON / v2 XML 序列化（emit）
```

要点：

- **入队点**：完成参数校验与图片解码后。这样坏请求不会占用等待位，错误码与现在一致；代价是等待期间保留图片内存，用容量上限约束（见 §12）。
- **worker 数固定为 1**：与 GPU 串行语义一致，避免并发写 CUDA 上下文。
- **队列只在进程内**：单进程部署；不引入 Redis/Celery 等外部依赖。
- **锁的角色变化**：`pose_lock` 由 worker 独占，不再被 HTTP 线程争抢；`GroundPoseEstimator._lock` 仅作为最后一道保险，正常路径无竞争。

## 5. 队列设计

### 5.1 数据结构

新增 `ground_pipeline/pose_queue.py`，不把队列逻辑塞进已经 3000+ 行的 `ground_service.py`。

```python
class QueueRejected(Exception):
    reason: str          # "queue_full" | "client_quota"
    snapshot: dict       # 用于错误响应

class QueueTimeout(Exception):
    waited_ms: float

@dataclass
class PoseJob:
    request_id: str
    client_key: str
    priority: int                 # 0..9，越小越优先
    seq: int                      # 入队序号，保证同优先级 FIFO
    enqueued_at: float
    ahead: int                    # 入队瞬间前面还有多少任务（含正在执行）
    state: str                    # pending | running | done | cancelled
    cancel: threading.Event
    started: threading.Event
    done: threading.Event
    result: tuple[int, dict] | None
    started_at: float | None
    finished_at: float | None

class PoseQueue:
    def __init__(self, capacity=16, per_client_limit=4,
                 wait_timeout_s=60.0, aging_s=30.0)
    def start(self, executor)                     # executor(job) -> (code, body)
    def submit(self, *, request_id, client_key, priority) -> PoseJob
    def wait(self, job, timeout_s=None) -> tuple[int, dict]
    def cancel(self, request_id) -> dict          # {found, state, ahead}
    def snapshot(self) -> dict
    def shutdown(self)
```

实现选择：

- `pending: list[PoseJob]` + `threading.Condition`，**不使用** `queue.PriorityQueue`。原因是需要按客户端计数、取消时精确移除、计算 `ahead`、以及 aging 后重新排序；`n ≤ 16` 时每次出队线性扫描成本可忽略。
- `executor` 由 `ground_service` 注入，内部执行「原 `_pose_single_pipeline` 的 GPU 段」，队列本身不依赖 FastAPI / torch，便于用假 executor 做单测。
- worker 为 `daemon=True` 的普通线程，在 lifespan 启动、在 lifespan 关闭时置停止哨兵并 `join(timeout=5)`。

### 5.2 调度规则

| 规则 | 定义 |
|---|---|
| 顺序 | 先按 `effective_priority` 升序，再按 `seq` 升序 |
| 优先级 | **仅服务端指定**，客户端不可传：`/v1|v2/pose/single` 默认 0，`/v1/ground` 内部姿势任务固定 5。保留内部 0..9 的整数空间供后续入口使用 |
| 防饿死 | `effective = max(0, priority - floor(waited_s / aging_s))`，`aging_s` 默认 30s，0 表示关闭；只在出队时计算，不修改任务本体 |
| 容量 | `capacity` 只统计 `pending`；`running` 不占等待位。满载时新请求立即 `503 queue_full` |
| 客户端配额 | 同一 `client_key` 的 `pending + running` 不超过 `per_client_limit`（默认 4），超出立即 `503 client_quota` |
| `client_key` | 请求体 `client_id`（新增可选，≤64 字符）> 请求头 `X-Pose-Client-Id` > 对端 IP。NAT 后多用户会共享 IP，故提供 `client_id` 覆写 |
| 等待超时 | `wait_timeout_s` 默认 60s，只约束「排队等待」，不约束执行；超时后撤销排队并返回 `queue_timeout`。取值与客户端 HTTP 超时对齐，保证超时响应能送达 |
| 执行耗时 | 不强制中断。单次执行超过 `exec_timeout_s`（默认 300s）只打 `pose_queue_stuck` 日志并把 `snapshot.running.overdue` 置 true，由运维决定重启 |

### 5.3 取消语义

`state["pose_tasks"]` 从 `dict[str, threading.Event]` 改为 `dict[str, PoseJob]`（或直接查询 `PoseQueue`），入队即登记。

| 任务状态 | `/v1|v2/pose/cancel` 行为 | 返回 |
|---|---|---|
| `pending` | 置 `state=cancelled`，`done.set()`，不执行；等待线程立即返回 | `200 {"cancelled": true, "state": "pending", "ahead": n}` |
| `running` | 仅 `cancel.set()`；由管线检查点（SAM3D 之后、retarget 之后、world 之前）返回 `status=cancelled`（沿用现状） | `200 {"cancelled": true, "state": "running"}` |
| `done` / 不存在 | 保持现状 | `404 {"cancelled": false, "error": "未找到任务"}` |

排队中取消不占 GPU，也不留 worker 空转（出队时跳过 `state != pending` 的任务）。

### 5.4 队列快照

`PoseQueue.snapshot()` 返回（供 `/v1/pose/queue` 与 health 使用）：

```json
{
  "capacity": 16,
  "pending": 3,
  "running": {"request_id": "6f87…", "exec_ms": 5200, "overdue": false},
  "per_client": {"192.168.139.1": 2, "studio-a": 1},
  "stats": {
    "admitted": 120, "completed": 117,
    "rejected_full": 4, "rejected_quota": 1,
    "timed_out": 1,
    "cancelled_pending": 2, "cancelled_running": 0,
    "avg_wait_ms": 2300, "p95_wait_ms": 6100, "avg_exec_ms": 7800
  }
}
```

`avg_*` / `p95_*` 基于最近 100 次样本（`wait_ms`、`exec_ms`）；`eta_ms` 用 `(ahead) * avg_exec_ms` 估算，仅用于给客户端参考。

## 6. 接口契约变更

### 6.1 请求字段（新增，全部可选，不传行为不变）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `client_id` | string | 空 | 公平配额键；为空时用 `X-Pose-Client-Id` 头或对端 IP |
| `queue_timeout_s` | number | 服务默认 | 本次排队等待上限；服务端再与 `--pose-queue-timeout` 取小值 |

> **不提供 `priority` 请求字段**：优先级由服务端按入口固定（交互=0、`/v1/ground`=5），避免客户端全用 0 导致 aging 失效。传入未知字段仍按现有逻辑被忽略，不报错。

### 6.2 成功响应（200）

在现有 body 上新增一个字段，其余字段与数值不变：

```json
"queue": {
  "priority": 0,
  "ahead": 2,
  "wait_ms": 3412.5,
  "exec_ms": 8421.0,
  "pending_at_start": 1,
  "eta_ms": 0
}
```

- `time_ms` 语义保持「请求总耗时」，包含排队等待；`queue.exec_ms` 为 worker 内实际执行耗时，二者之差约等于 `queue.wait_ms` 加序列化开销。
- `queue.priority` 是服务端分配值（只读），客户端无法指定。
- v2 XML 响应**不新增节点**（序列化器由外部资产提供），队列信息只在 JSON 路径可见；v2 客户端行为就是「多等一会儿」。

### 6.3 队列拒绝与超时（503）

沿用 503，避免旧客户端新增状态码分支；用 `error_code` 区分原因，并加 `Retry-After` 头。

```json
{
  "status": "error",
  "engine": "sam3d_vitpose",
  "request_id": "…",
  "error": "queue_full: 队列已满（16/16），请稍后重试",
  "error_code": "queue_full",
  "queue": {"pending": 16, "capacity": 16, "running": true, "eta_ms": 54000},
  "retry_after_s": 2
}
```

| `error_code` | HTTP | `Retry-After` | 触发 |
|---|---|---|---|
| `queue_full` | 503 | 2 | pending 达到 `capacity` |
| `client_quota` | 503 | 5 | 同一 `client_key` 的 pending+running 达到 `per_client_limit` |
| `queue_timeout` | 503 | 5 | 排队等待超过 `queue_timeout_s` |

> 不从 503 改为 429：现有插件与脚本按 503 做了重试/降级，改码需要客户端同步发版，收益不足。

### 6.4 取消

- 排队取消立即返回（见 §5.3），`state` 字段区分 `pending` / `running`。
- 等待中的 `POST /v1|v2/pose/single` 在 `state=cancelled` 时返回 `200 status=cancelled, error="任务已取消"`（沿用 `_pose_cancelled_body`），并带上 `queue.wait_ms`。

### 6.5 队列状态接口（新增）

`GET /v1/pose/queue`（JSON，只读，无图片内容）：

直接返回 `PoseQueue.snapshot()`，另加 `worker_alive`、`version`。用于排障与客户端自适应（例如 `pending > 8` 时降低提交速率）。

`GET /v1/pose/health` 增加 `queue` 摘要（不改变现有字段）：

```json
"queue": {"enabled": true, "capacity": 16, "pending": 3, "running": false}
```

`/v2/pose/health` 的 XML 结构不变（`health_to_xml_bytes` 忽略额外键），避免影响 Max 客户端握手。

### 6.6 `/v1/ground` 的姿势分支

- `pose_inference=true` 时，姿势任务以服务端内部优先级 5（低于交互的 0）提交到同一队列，等待上限取 `min(队列默认值, 请求剩余时间)`。
- 入队被拒或等待超时：**不影响地面结果**，仅把 `pose` 置为 `{"status": "error", "error_code": "queue_full|queue_timeout", "error": "..."}`。
- 该分支在 `run_in_threadpool` 中等待，避免阻塞事件循环（现有实现在事件循环里直接跑同步推理，本计划只包住新增的等待逻辑）。

### 6.7 Prometheus 指标端点（新增）

`GET /metrics`，`text/plain; version=0.0.4`，无鉴权（与现有接口一致，部署在内网），不依赖 `prometheus_client`（手写文本，避免新增依赖）。

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `pose_queue_pending` | gauge | — | 当前等待数 |
| `pose_queue_capacity` | gauge | — | 容量 |
| `pose_queue_running` | gauge | — | 0/1 |
| `pose_queue_per_client` | gauge | `client` | 各客户端 pending+running |
| `pose_queue_admitted_total` | counter | — | 累计入队 |
| `pose_queue_completed_total` | counter | `status`（success/error/cancelled） | 累计完成 |
| `pose_queue_rejected_total` | counter | `reason`（queue_full/client_quota） | 累计拒绝 |
| `pose_queue_timed_out_total` | counter | — | 累计排队超时 |
| `pose_queue_cancelled_total` | counter | `state`（pending/running） | 累计取消 |
| `pose_queue_wait_seconds` | histogram | `le` | 排队等待时长（桶：0.5/1/2/5/10/20/30/60） |
| `pose_queue_exec_seconds` | histogram | `le` | 执行时长（桶：1/2/5/10/20/30/60/120/300） |

- 与 `GET /v1/pose/queue` 共用 `snapshot()`/统计计数，不重复维护状态。
- `client` 标签按 `client_key` 输出，可能包含 IP 或 `client_id`；如担心基数，可在配置里关闭该标签（见 §8 `--pose-metrics-client-label`）。
- 标签值做转义（`\`、`"`、换行），避免抓取端解析失败。

## 10. 实施步骤

**P0（本计划主体）**

1. 新建 `pose_queue.py`：任务、容量/配额、优先级+aging 出队、取消、快照、统计；单测用假 executor 覆盖。
2. 拆分 `_pose_single_pipeline` 为 `_pose_prepare` / `_pose_execute`；把 GPU 段交给 worker，HTTP 线程只负责提交与等待。
3. `create_ground_app`：初始化 `state["pose_queue"]`，lifespan 启动 worker、关闭时 `shutdown`；删除非阻塞锁早退。
4. cancel 路由改查队列，支持 pending 快速取消与 `state` 字段。
5. 成功响应加 `queue`，错误响应加 `error_code` / `queue` / `retry_after_s` / `Retry-After`。
6. 新增 `GET /v1/pose/queue`；`_pose_health` 加 `queue` 摘要。
7. 新增 `GET /metrics`：`pose_queue.render_prometheus()` 输出文本格式（gauge/counter/histogram），默认关闭 `client` 标签可用参数切换。
8. `/v1/ground` 的 `pose_inference` 分支接入队列（低优先级 + 失败降级为 `pose.status=error`）。
9. 更新 `GROUND_SERVICE_API.md` §3.3 / §6。

**P1（后续，不阻塞 P0）**

- 断开感知：客户端 HTTP 断开后自动取消执行中的任务（`request.is_disconnected` 轮询或 anyio cancel scope），释放 GPU 给下一位。60s 等待上限下，这个能力决定槽位回收速度，建议紧随 P0 落地。
- 内存预算准入：除任务数外，按排队图片字节总量（如 256 MB）拒绝，替代单纯容量上限。
- 队列等待期间的「预估完成时间」按最近同类任务耗时（是否 `want_mesh`、是否 `ground_mode=infer`）分桶估算，提高 `eta_ms` 精度。
- v2 XML 可选 `<queue>` 节点（需与参考序列化器资产同步，独立专项）。
- 多实例部署时的外部队列（Redis 等）：非本期目标。

## 11. 测试与验收

### 11.1 单元测试（无 GPU）

- 容量：第 `capacity+1` 个提交抛 `QueueRejected(queue_full)`。
- 顺序：同优先级严格 FIFO；低 `priority` 值先执行。
- aging：高优先级连续占用时，等待超过 `aging_s` 的低优先级任务被提升。
- 配额：同一 `client_key` 第 `per_client_limit+1` 个抛 `client_quota`；不同 key 互不影响。
- 超时：`wait_timeout_s` 到期返回 `QueueTimeout`，且任务不再被执行。
- 取消：pending 取消后 worker 不执行、等待线程立即返回；running 取消只置事件。
- 统计：`snapshot()` 的 `pending`/`avg_wait_ms`/`rejected_*` 与操作次数一致。
- 指标：`render_prometheus()` 输出可被 `promtool check metrics` 通过（或按行正则校验），计数值与操作次数一致；关闭 `client` 标签后无 `client=` 字样。
- 并发：20 个线程同时提交，只有 1 个 running，其余 pending 顺序与 `seq` 一致。

### 11.2 集成测试（真机，`--sam3d-resources`）

- 并发 4 个 `/v1/pose/single`：全部 200，`queue.ahead` 分别为 0/1/2/3，`wait_ms` 递增；无 503。
- 并发 20 个：前 16 个入队，其余立即 `503 queue_full` + `Retry-After`；地面接口 `/health` 仍正常。
- 排队中取消：第 3 个任务的 `request_id` 调 `/v2/pose/cancel`，响应 < 200ms 且 `state=pending`；对应 `/v2/pose/single` 返回 `status=cancelled`；第 4 个任务顺延。
- 单请求回归：与改造前相比，`time_ms` 增量 < 20ms，`queue.wait_ms ≈ 0`，响应数值逐字段一致。
- `/v1/ground` 回归：`pose_inference=false` 的耗时与结果不变；`pose_inference=true` 与姿势接口并发时，地面结果不受影响，姿势最坏返回 `queue_timeout`。
- `/v1/pose/queue` 与实际排队数一致；`/v1/pose/health` 字段只增不改。
- `/metrics` 可被 Prometheus 抓取（`promtool check metrics` 或 `curl` 后正则），`pose_queue_pending` 与 `/v1/pose/queue` 的 `pending` 一致。
- 等待超时：构造 1 个长任务占住 worker，再提交多个任务，验证第 60s 附近返回 `503 queue_timeout`（客户端超时设为 ≥ 65s）。

### 11.3 验收标准

1. 容量内并发请求 100% 成功，不再出现 `GPU 忙`。
2. 排队取消端到端 < 1s；执行中取消在下一个检查点生效。
3. 队列开销（入队+唤醒）单请求 < 20ms。
4. 任何队列拒绝/超时都不影响 `/v1/ground`、`/health` 与其他已返回结果。
5. v2 XML 响应结构与改造前逐字段一致。

## 12. 风险与权衡

| 风险 | 说明 | 处置 |
|---|---|---|
| 图片内存 | 入队前已解码图片，`capacity=16` 时最坏约 16×40MB | 默认容量 16；P1 加字节预算准入；文档写明 40MB 上限 |
| worker 卡死 | CUDA 异常/驱动挂起会让队列整体停摆，无法安全中断内核 | `exec_timeout` 只告警并在 `/v1/pose/queue` 标 `overdue`，由运维重启；不自动杀线程（会破坏 CUDA 上下文） |
| 客户端 HTTP 超时 | 客户端先断开，任务仍占槽位 | 等待上限取 60s 与常见客户端超时对齐；客户端超时需 ≥ 65s；P1 尽快补断开感知取消 |
| NAT 共享 IP | 办公室多人经同一出口 IP 提交，配额会互相影响 | 提供 `client_id` / `X-Pose-Client-Id` 覆写；默认 4 已留余量 |
| 优先级 | 优先级只由服务端入口决定，客户端无法插队 | 无需额外防护；aging 仍保留，防止未来新增低优先级入口被饿死 |
| 指标基数 | `client` 标签可能出现大量 IP / 随机 `client_id` | 提供 `--pose-metrics-client-label=0` 关闭；`client_id` 长度限制 64 |
| 队列与地面互斥 | 姿势队列长期繁忙会推迟 `/v1/ground` 的 CPU/GPU 段 | 地面接口的姿势部分用低优先级；地面本身的 DepthPro/LangSAM 不在本队列内（现状不变），需在文档写明两者仍共享 GPU |
| 回滚 | 新调度出问题时需要快速回到旧行为 | `--pose-queue-size=0` 即恢复「忙则 503」；代码不删旧错误分支 |

## 13. 已确认决策（2026-10-26）

| 决策项 | 结论 |
|---|---|
| 队列容量 | `16`（内存可控优先，突发再靠 P1 字节预算准入扩展） |
| 排队等待上限 | `60s`（与客户端 HTTP 超时对齐；需确认 Max 插件侧超时 ≥ 65s，见下方待办） |
| `priority` 暴露 | 不暴露，仅服务端按入口固定；`/v1|v2/pose/single`=0，`/v1/ground`=5 |
| Prometheus 端点 | 实现 `GET /metrics`，手写文本格式，不引入新依赖；`client` 标签可配置关闭 |

**落地前唯一剩余待办**：确认插件侧（Max 客户端）单次请求 HTTP 超时值。若小于 65s，则把 `--pose-queue-timeout` 下调到「插件超时 − 5s」，否则 `queue_timeout` 响应会因客户端已断开而无人接收。
